# Blackjack operating notes

## Ownership
- Canonical development branch: `feature/blackjack`.
- Owned roots: `artifacts/cascade-8/src/blackjack`, `artifacts/api-server/src/blackjack`, `lib/db/src/schema/blackjack.ts`.
- Shared route mounting, shared wallet/session primitives, schema aggregation, package files, preview infrastructure and promotion machinery remain platform-owned.
- Replit remains a preview/runtime consumer on `integration/replit-preview`; normal Blackjack source development happens on `feature/blackjack` only.

## Product direction
- Single-player blackjack table with exactly five seats. The same player may occupy and play any subset of 1–5 seats simultaneously.
- Desktop visual target is the approved 16:9 premium live-casino mockup: dark green felt, dark leather rail, restrained gold trim, dealer centered behind the table, five seat arc, compact top HUD and integrated bottom betting/action console.
- Mobile will preserve the same table identity in portrait rather than becoming a generic control dashboard.
- `TABLE MIN` exists. There is no `TABLE MAX` label or configured table maximum; the natural affordability ceiling is the player's available shared wallet balance.
- Pre-deal `X2 BET` doubles the selected seat's wager and is distinct from in-round Blackjack `DOUBLE`/double-down.
- Pre-deal controls must support chip placement, last-chip undo, clearing a selected wager, and clear seat state feedback.
- Empty seats expose a clear `TAKE SEAT` / `TAP TO SIT` affordance. Occupied, selected, bet-ready and in-round states are visually distinct.
- Rules baseline: 6-deck shoe, ~75% cut-card reshuffle after a completed round, dealer hits soft 17, Blackjack pays 3:2, normal win 1:1, push returns stake, insurance pays 2:1, normal split hands may reach four hands, DAS is enabled, and split Aces receive one card each with no resplit/DAS.
- The shared `shared_wallets` row and root-scoped `game_session` remain the only live wallet/session authorities; Blackjack never creates an independent spendable wallet.

Same-tab actions are serialized by a client queue and build their request only when they reach the front, so rapid clicks consume revisions in order. Backend session advisory lock + row lock + monotonic revision means two tabs holding the same revision cannot both advance the round: one commits, the other receives `BLACKJACK_STALE_REVISION`. - 2026-10-08 — Part 10B shared-wallet authority complete — Blackjack monetary actions now use the platform `shared_wallets` row rather than a game-local balance. A Blackjack-owned repository executes each action under PostgreSQL advisory locks and one DB transaction: it locks/creates the canonical shared wallet, loads the persisted Blackjack table state, validates/executes the authoritative round transition, requires the pre-existing wallet balance to cover any new stake, applies the wallet delta, persists round/shoe/revision state, writes round audit + signed ledger entries, stores an idempotent action receipt, then commits. DEAL debits the sum of all participating seat stakes; INSURANCE debits exactly half the active main wager; DOUBLE and SPLIT/RESPLIT each debit one matching active-hand wager. When the action completes the round, all main-hand returns plus insurance returns are credited in that same transaction, including immediate natural/dealer-Blackjack settlements. A payout generated by DOUBLE/SPLIT does not bypass affordability: the extra stake must be coverable before the future return is credited. `POST /blackjack/action` now requires a 12–100 char idempotency key; same-key/same-request replay returns the stored snapshot without moving money twice, while key reuse for a different request/session is rejected. Public snapshots include the real shared-wallet `balanceCents`. New Blackjack-owned persistence covers table state, round audit, action receipts and ledger; no separate Blackjack wallet exists and there is still no configured table maximum beyond numeric safety + shared-wallet affordability. Runtime table creation stays inside the Blackjack repository and the canonical `lib/db/src/schema/blackjack.ts` definitions are present; shared schema aggregation and `/api` router mounting remain platform-owned integration steps. Pure regression coverage checks DEAL, DOUBLE, SPLIT, insurance and same-action completion payout accounting; GitHub CI/runtime execution is still not available in this branch session.

- 2026-10-08 — Part 9 INSURANCE complete — dealer Ace upcard now enters a dedicated `insurance` phase before any player action or hole-card reveal. Each participating initial hand is offered insurance in deterministic seat order; accepted insurance is exactly half the main wager and remains a separate side-bet ledger (`insuranceWager`, `insuranceReturnAmount`, `insuranceNetAmount`) rather than being merged into main-hand settlement. After the final decision, the dealer peek resolves: dealer Blackjack pays accepted insurance at 2:1 profit (3x stake returned) and immediately settles the main round; no dealer Blackjack loses accepted insurance and continues into the first playable hand. Declining insurance carries zero stake/loss. An already-settled insurance side bet is preserved on only one descendant if the main hand later splits, preventing accidental duplication. The UI hides the dealer hole card throughout the insurance decision phase, exposes `INSURANCE / NO INSURANCE`, shows the required half-wager amount, includes placed insurance in live TOTAL BET, marks the active mobile seat as `INS`, and renders insurance side-bet status independently from the main-hand result. Regression coverage now includes Ace-upcard insurance entry, 2:1 insurance payout, losing/declined insurance, multi-seat decision progression and no-duplication through later SPLIT.
- 2026-10-08 — Part 8B advanced SPLIT complete — normal split hands may now be resplit until a seat reaches a hard maximum of four simultaneous hands; stable tree-style `handId`s plus reindexed `handIndex` values preserve deterministic same-seat action order after each insertion. Double After Split is enabled on any eligible two-card non-Ace split hand and still consumes exactly one card before forced stand/bust. Splitting Aces has dedicated rules: each Ace child receives exactly one card, is immediately stood, cannot HIT/DOUBLE/resplit, and any resulting 21 remains a normal split 21 rather than a 3:2 natural. UI now exposes `RESPLIT`, shows `MAX 4` when the seat cap is reached, distinguishes Ace-split locked hands, supports 3–4 hands in a compact 2×2 seat layout, keeps per-hand results/wagers visible, and includes all copied/doubled stakes in live TOTAL BET.
- 2026-10-08 — Part 8A base SPLIT complete — round hands now have stable `handId`, `handIndex` and `splitDepth`, while `activeHandId` becomes the true action cursor and `activeSeatId` remains a derived UI-compatible seat pointer. Part 8A performs one split only: it copies the original wager to a second independent hand, consumes exactly one new shoe card for each child hand, keeps both hands under the same seat, and progresses actions as `Hand 1 -> Hand 2 -> next seat`. A two-card 21 created by a split is a normal 21/stand, never a natural Blackjack payout.
- 2026-10-08 — Part 7 in-round DOUBLE complete — the active hand may double only while it is still `PLAYING`, still has exactly its original two cards, and has not already doubled. A successful DOUBLE records an additional stake equal to the current hand wager by doubling the round wager, consumes exactly one shoe card, then forces the hand closed as `STOOD` or `BUST` and immediately advances to the next playable seat/dealer. Settlement uses the doubled wager.
